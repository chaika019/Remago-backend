# Ревью backend — 21 сентября 2026

Проверены основные цепочки auth/security, роли, CRM, компании/контакты, график,
календарь, документы/импорт, уведомления, Drive, конфигурация и скрипты.
Это статическое ревью с локальными unit-тестами, не полноценный прогон всех API.
PostgreSQL, SMTP, Telegram, Google Drive и Gotenberg в рамках ревью не запускались.
Рабочая папка не предоставляет доступную Git-историю; сравнения с предыдущей версией нет.
Содержимое `.env` не использовалось: замечания о конфигурации относятся к defaults.

P0 — немедленное исправление; P1 — безопасность/потеря данных/сломанная функция;
P2 — функциональные ошибки и эксплуатационные проблемы.
Кроме пункта 1, перечисленные проблемы пока не исправлены.
Пути ниже относительно корня проекта; номера строк относятся к состоянию этого ревью.

## 1. P0: вход в подтверждённый аккаунт без пароля и кода — исправлено

**Код:** `src/main/java/com/adrotation/crm/auth/service/EmailVerificationService.java:73`,
`auth/service/AuthService.java:112` (остальные сокращённые пути Java — внутри `src/main/java/com/adrotation/crm/`).

Публичный `POST /api/auth/verify-email` принимает email и шестизначный код.
Раньше `verify()` немедленно возвращался, если email уже подтверждён;
`AuthService.verifyEmail()` после этого создавал сессию и JWT.
Достаточно было знать email любого включённого подтверждённого пользователя,
включая SUPER_ADMIN. Пароль и административный второй фактор обходились.

Исправление: для уже подтверждённого аккаунта выбрасывается BusinessException;
повторное использование подтверждения регистрации не создаёт новую сессию.
Добавлен `EmailVerificationAuthenticationTest`: все 10 ролей, повторное использование
кода после успешной регистрации, неправильный код. На старом коде 11 из 12 новых
проверок падали; положительный сценарий регистрации сохранён.

Изменение в исходниках само по себе не обновляет запущенный сервер и не отзывает
сессии, созданные до исправления. При развёртывании исправления следует завершить
существующие сессии. Это ревью не устанавливает, использовалась ли уязвимость.

## 2. P1: счётчик ошибок 2FA откатывается

**Код:** `auth/service/AuthService.java:71`, `security/service/TwoFactorService.java:72`.

Внутренний `verify()` имеет `noRollbackFor=BusinessException`, но присоединяется
к транзакции внешнего `verifySecondFactor()`. Последний повторно выбрасывает ошибку
и откатывает всю транзакцию, включая увеличение `attempts`.
Лимит в 5 попыток на challenge не сохраняется между запросами. Rate limit на IP
остаётся отдельной защитой, но не заменяет лимит challenge.

Исправление: согласовать границы/правила отката. Регрессионная проверка нужна
через Spring proxy и PostgreSQL, с перечитыванием attempts после каждого запроса.

## 3. P1: неудачные входы отсутствуют в журнале

**Код:** `auth/service/AuthService.java:45`, `security/service/AuthAttemptService.java:19`.

Запись неудачного входа выполняется в той же транзакции, что и login.
Следующий UnauthorizedException откатывает запись. Аналогично теряются ошибки 2FA.
Панель безопасности показывает неполную картину попыток входа.

Исправление: сохранять события неуспешной аутентификации в независимой транзакции
или явно отделить их от транзакции выдачи сессии. Проверить сохранение через БД.

## 4. P1: один 2FA challenge можно использовать конкурентно

**Код:** `security/service/TwoFactorService.java:74`,
`security/repository/TwoFactorChallengeRepository.java`, `security/entity/TwoFactorChallenge.java`.

Challenge читается обычным findById, без блокировки и без @Version.
Два параллельных запроса с верным кодом могут оба увидеть consumedAt=null
и выдать две сессии. Конкурентные неправильные коды также теряют инкременты.

Исправление: блокировать challenge на время проверки и потребления;
проверить двумя транзакциями, что успешно завершится только одна.

## 5. P1: снятые роли остаются в действующем JWT

**Код:** `user/service/UserService.java:45`, `config/SecurityConfig.java:35`,
`security/service/UserSessionService.java:46`.

assignRoles меняет БД, но не отзывает сессии. @PreAuthorize использует роли из JWT;
валидация сессии проверяет enabled/email/срок, но не актуальность ролей.
После снятия SUPER_ADMIN старый токен продолжает проходить контроллерные проверки,
например создание/изменение календарных событий. Некоторые сервисы перепроверяют
роли в БД, другие — нет. По умолчанию окно до 480 минут.

Исправление: отзывать сессии при смене ролей либо проверять версию прав/строить
authorities по актуальному пользователю.

## 6. P1: публично известный JWT secret используется по умолчанию

**Код:** `src/main/resources/application.yml:80`, `docker-compose.yml`.

При отсутствии JWT_SECRET_BASE64 сервер запускается с ключом из репозитория.
Пользователь с собственной активной сессией может подписать токен с изменёнными
ролями, сохранив свои email и sid; SessionValidationFilter не сверяет роли.
Это условная проблема конфигурации: реальное значение `.env` не проверялось.

Исправление: обязательный секрет для обычного запуска, отказ от demo-ключа;
демонстрационный режим — только явно выбранный профиль.

## 7. P1: договоры перезаписывают файлы друг друга

**Код:** `documents/service/ContractService.java:86`,
`documents/service/LocalDocumentStorageService.java:40`.

У одной компании допустимы номера A/1 и A-1, но после очистки оба дают A-1.
Имя файла одинаково, Files.write использует TRUNCATE_EXISTING.
Второй договор заменяет DOCX/PDF первого; DocumentVersion тоже хранит эти пути.
При ошибке cleanup второго договора может удалить файл первого.

Исправление: включать уникальный ID договора/версии в имя файла. Для уже созданных
коллизий изменение генератора не восстановит старые байты; нужны резервные копии.

## 8. P1: оба планировщика записывают уведомления в read-only транзакции

**Код:** `crm/scheduler/CrmReminderScheduler.java:26`,
`schedule/scheduler/ShiftReminderScheduler.java:27`.

Внешняя транзакция readOnly=true, а NotificationService присоединяется к ней
и делает INSERT. Для PostgreSQL с текущей JPA-конфигурацией это конфликт записи
с read-only транзакцией. Ошибка проявится, когда найдётся запись для напоминания;
пустой набор данных скрывает проблему. На живой БД в этом ревью не воспроизводилось.

Исправление: разрешить запись во внешней транзакции либо отделить чтение кандидатов
от транзакционной записи уведомлений. Добавить интеграционную проверку scheduler.

## 9. P1: перенос CRM-карточки ломает последующую нумерацию

**Код:** `crm/service/DealService.java:329`,
`src/main/resources/db/migration/V1__init.sql:117`.

Следующий номер вычисляется как count+1. Создать карточки 1,2,3 на одну дату,
перенести карточку 2 на другую дату: остаются номера 1,3. Следующее создание
получит 3 и нарушит уникальность (manager, activity_date, daily_sequence).
Блокировка менеджера не исправляет пропуски последовательности.

Исправление: max(dailySequence)+1 под существующей блокировкой.

## 10. P2: синхронизация Drive падает на папке без номера недели

**Код:** `schedule/service/WeekService.java:61`.

extractWeek("Архив") возвращает null; Map.entry(null, folder) бросает NPE
до выполнения следующего filter. Одна посторонняя папка ломает всю синхронизацию.

Исправление: отфильтровать нераспознанные номера до создания Map.entry.

## 11. P2: график возвращает неполный диапазон недель

**Код:** `schedule/service/ScheduleService.java:30`.

Создание недели по дате/импорт может оставить в БД только часть года.
При запросе, например, недель 1–10 и наличии только недели 5 range не пуст,
поэтому syncYear не вызывается и ответ содержит одну неделю вместо десяти.

Исправление: обеспечивать наличие каждой запрошенной недели, а не проверять
только полное отсутствие диапазона. Учитывать конкурентное создание недель.

## 12. P2: чтение CRM может попытаться создать неделю в read-only транзакции

**Код:** `crm/service/DealService.java:56`, `schedule/service/WeekService.java:95`.

list() с readOnly=true вызывает requireByIsoWeek(), который при отсутствии недели
сохраняет новую запись в той же транзакции. Запрос пустой CRM на ещё не созданную
неделю должен возвращать пустой список, но вместо этого пытается сделать INSERT.

Исправление: разделить поиск недели и её создание. Проверить на чистой БД.

## 13. P2: отправка обходит правила статусов документов

**Код:** `documents/service/DocumentDeliveryService.java:81`,
`documents/service/DocumentWorkflowService.java:26`.

Workflow запрещает переходы из ARCHIVED, но deliver() при успешной отправке
без проверки текущего статуса присваивает SENT. Архивный документ с файлом
можно вернуть в SENT, минуя workflow; аналогично обходятся стадии согласования.

Исправление: единая проверка разрешённой отправки до внешнего вызова,
единое обновление статуса и аудит. Саму отправку в этом ревью не выполняли.

## 14. P2: ограничения доступа к компаниям расходятся между API

**Код:** `company/workspace/CompanyWorkspaceService.java:42`,
`company/service/CompanyService.java:40`, `company/service/CompanyService.java:159`,
`company/controller/CompanyController.java`.

Workspace запрещает менеджеру чужую компанию без его сделок/авторства.
Прямые get/search/contacts обходятся без этой проверки; разрешённые менеджеру
updateStatus/addContact/updateContact/deleteContact тоже не проверяют владельца.
Итого запрет workspace обходится прямыми запросами к компании и контактам.

Исправление: согласовать продуктовую модель доступа (общая база или изоляция
менеджеров) и применить её одинаково во всех маршрутах. Сейчас правила противоречат друг другу.

## 15. P2: лимит результатов применяется раньше ограничения по менеджеру

**Код:** `search/service/GlobalSearchService.java:47`.

Поиск берёт 20 последних сделок всех пользователей, затем выбрасывает чужие.
Если 20 более свежих совпадений принадлежат другим менеджерам, собственная
совпадающая сделка не попадает в результат, хотя доступ к ней есть.

Исправление: managerId включить в запрос БД до LIMIT. Аналогичную схему проверить
для поиска компаний и спецификаций.

## Проблемный код и эксплуатационные ограничения

- `DocumentLibraryService.list()` сначала загружает все документы трёх таблиц,
  преобразует связанные сущности, фильтрует/сортирует в JVM, затем берёт страницу.
  Даже size=1 делает работу по всему архиву; возможны дополнительные lazy-запросы.
  Нужны фильтрация, сортировка, COUNT и пагинация на стороне БД.
- Правила ролей продублированы в контроллерах, UserAccessPolicy, CRM, workspace,
  поиске и календаре. Уже отличаются трактовки MANAGER+DIRECTOR; permissions
  не являются единым источником серверных разрешений.
- `SpecificationService` дублирует расчёты сумм/НДС и генерацию файлов для ручного
  и CRM-сценария. Изменение одного пути легко оставляет другой с иной арифметикой.
- Сетевые отправки/конвертация документов происходят внутри транзакций БД.
  Внешний успешный вызов не откатывается вместе с БД. Нужен устойчивый учёт задач
  и результатов отправки; при масштабировании — outbox/worker.
- Обработка ошибок генерации PDF местами просто проглатывает исключение
  (`ContractService`); `SessionValidationFilter` превращает любое RuntimeException,
  включая сбой БД, в 401 «сессия истекла». Это скрывает причины инцидентов.
- Auth/2FA до этого ревью не имели тестов. Старые 12 тестов проходили при P0.
  Нет интеграционной проверки транзакций PostgreSQL, конкурентности и отзыва прав.
- README устарел: обещает seed-пользователей и SEED_ENABLED=true, тогда как
  текущий SeedDataConfig создаёт цели/недели, Compose по умолчанию выключает seed;
  перечислены только V1–V3 при наличии V1–V8.
- `scripts/backup-postgres.sh` сохраняет только БД. Отдельный volume с DOCX/PDF
  в этот backup не входит; восстановление одной БД не возвращает документы.
- Скрипты Excel — одноразовый импорт конкретной книги: фиксированные листы,
  годы, owner ID/email и пути. Не выдавать их за универсальный импорт;
  рефакторить при повторном использовании, сохраняя исходные данные и сверку.
